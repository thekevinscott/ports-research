The plan is in two halves. Preparatory work is everything that has to be true
before a v2 run is banked. Post-run work is everything done to the banked runs.
The re-run sits between them.

## Process

Applies to both halves.

**Journal.** `JOURNAL.md` at the repo root. Append-only, one entry per major
event, UTC timestamp on each. Lab notes, not a changelog: what was done, what was
found, what was decided. Agents and Kevin both write to it. Session handoffs
under `internal/` keep their job, which is carrying state between sessions.

**Branches.** Every change is a branch in `.worktrees/<branch>`, the branch and
directory named identically, dashes only, opened as a PR. Kevin merges. The rule
already exists verbatim in agent-transcript-viewer's `AGENTS.md`; the first PR
after this one copies it into this repo's `AGENTS.md` and adds `.worktrees/` to
`.gitignore`. Run data is committed and the pack is 23 MB, so a worktree
checkout is cheap.

**One concern per PR.** Splitting is cheap and reviewing is not.

## Preparatory work

Order matters within this half. Each item is one or more PRs.

### 1. Whitelist

The agent's tree is assembled by `shutil.copytree` over the derived source,
followed by three removers. `remove_colocated_tests.py` globs `*_test.py` and
`*.test.ts`, so bytecode under `__pycache__` survived and four runs decompiled
it. The fix is an allow set over the copy: only paths matching the set are
copied, everything else is left behind and counted in the manifest. The library
itself is not touched; footnote 2 of the post still holds.

> I chose a blacklist rather than a whitelist because I wanted to modify the
> underlying library as little as possible, to remain faithful to the original
> impetus of acting on an entirely pre-agentic library.

Kevin, 2026-09-16:

> the whitelist should be made generic, and there should be a way to define it
> from gbnf-experiment

So the mechanism and the set live in different packages. Today porting-harness
takes a finished tree and knows nothing about how it was assembled; every
remover is gbnf-specific code in `gbnf_experiment/prepare_filesystem/`. Under
the whitelist, porting-harness owns the copy-by-allow-set step and its tests,
with no knowledge of gbnf. gbnf-experiment passes the set, which is the only
place gbnf's layout is named. The three removers go away; what they removed is
whatever the set does not name.

First test is a fixture tree with a `__pycache__/*_test*.pyc` entry, red before
green. The existing `TREE` fixture in `remove_colocated_tests_test.py` has no
such entry, which is why the unit tier never caught it.

One deferred decision lands in the same PR series. The reference's
`pyproject.toml` `testpaths`, its `Makefile` test targets and
`vitest.config.unit.ts` `include` still advertise the withheld test layout. The
2026-09-07 note said "Raise it with Kevin if that signal matters." Decision
owed: strip them under the whitelist, or accept the disclosure.

### 2. Prompt

Today it is two lines:

```
Port reference_implementation/ to {target_language} in ported_implementation/.
Run tests/ and iterate until green.
```

The second line points at a directory that `assemble_reference_implementation.py`
creates empty and the harness mounts read-only. All five no-tests runs wrote
there, hit `EROFS`, probed `mount`, and relocated. In the target-tests cell the
provided suite was green on first invocation in five of five runs. Neither cell
exercised iteration. Kevin, 2026-09-16: "we'll want to update the prompt too".
The new wording is settled in its own PR, and one wording runs across every arm.

### 3. API coverage tier, and removing the shim

A test suite over gbnf's public surface: exported names, signatures, and
behavior at the boundary. Separate from the integration suite, which drives
behavior and says nothing about how it is reached. Kevin, 2026-09-16: "I want to
be able to remove the shim".

The shim is `execute-test-suite`'s adapter pair, `adapt_python.py` and
`adapt_typescript.py`. It exists because, in the post's words, "Ports not
provided target tests often got behavior right and API surface wrong", and the
integration suite could not run against them unadapted. It rewrites a port's
surface onto the reference API at grading time and records which rules fired.
The 2026-09-07 note that asked for "exercising the public API surface (i.e.,
SDK)" was tabled then as "most dubious"; it is now in.

Two things follow. A port that passes the API suite needs no adapter, so the
adapter and its rules can go, and the graded result is the port as the agent
left it. And whether the API suite ships in the agent's `tests/` mount is a
design variable, same as the integration suite is today. Decision owed in the
API PR.

### 4. Agents and models

The post asks the question directly:

> Is the ports' similarity due to the fact that I used a single model, and it
> has a house style when it comes to writing code?

Kevin, 2026-09-16:

> pi will be done with openrouter, codex with openai, and claude with its
> denizens

Three agents, three providers, three allowlisted hosts. Claude already runs
against `api.anthropic.com`. `PiAgent` exists in agent-harness-sandbox with an
`openrouter` provider pointing at `openrouter.ai` and is not wired up. Codex
goes through OpenAI; `internal/MULTI_HARNESS_RESEARCH.md` records that its
bubblewrap sandbox fails under `cap_drop: ALL`, so Codex has an engineering
problem to solve before it has a host to allowlist. The allowlist rule applies:

> It's ok to whitelist a handful of URLs but let's do them one by one

One agent per PR, one host per PR, one live pilot run each before any matrix.

**Thinking text.** Every `thinking` block in every banked v1 transcript is
empty. The 2026-09-07 investigation ruled the harness out: the transcript is a
direct read-write bind mount, nothing in the three packages touches thinking
blocks, and outside the harness `claude-opus-5` through the Claude Code CLI
writes zero thinking text in 26,520 blocks while `claude-fable-5`,
`claude-fable-5-1`, `claude-haiku-4-5` and `claude-opus-4-6` write it into the
same format. The reasoning is on disk only as an encrypted `signature`. Kevin,
2026-09-16: "add this to the list of things to fix". The lever is the model or a
CLI setting, not the harness. Each agent's pilot run has to show non-empty
thinking text before it is used in the matrix. Otherwise the post-run
transcript questions stay unanswerable for v2 as well.

## The run

Redo scope was left on 2026-09-14 as "surgical 8 vs full re-run", Kevin's call.
The whitelist settles it: any assembly change moves the corpus the model sees,
so every v1 run becomes a prior harness generation. Full re-run of the 40 cells
under one pinned harness and one derivation, tagged `v2`.

v1 was 40 runs on one model at median 6.5M tokens and 13 minutes per run. Three
agents make it 120. Whether all three run the full matrix or a subset is
Kevin's call after the pilots.

### 7. Analysis

A learning track, not a build track. Embeddings and AST metrics both exist and
neither has a reading Kevin trusts.

> I don't want to drop it but I want to ignore it for now

> I'm still not sure how to interpret any of the AST stuff

The literature review (`internal/LITERATURE_2026-09-09-code-embeddings.md`, 43
references) found embeddings track surface similarity, not correctness, and
recommended calling the measure structural drift. Seven AST measures including
cyclomatic complexity are computed for every run and displayed nowhere; the
notebook shows only file count and LOC. Deliverables, in order: the
plain-language explainer Kevin asked for on 2026-09-10 ("how to tell whether
something is close or not, in a way that a mid-to-senior SWE can understand"),
then a decision on which measures reach the notebook.

The literature review is already done. `SYNTHESIS.md` and `papers/INDEX.md` are
in the repo; `internal/LITERATURE_2026-09-09-code-embeddings.md` and
`internal/LANDSCAPE.md` are not. No new survey work.

### 8. Mistral review

Their case study (mistral.ai/news/legacy-code-modernization/) did three things:
a numerical parity harness before any translation; a documentation pass where
100+ agents worked leaf-up over a caller-callee tree; and a human-supervised
coder/tester/reviewer loop after a fully autonomous pass produced "Fortran
retyped in C++ syntax". The scaffold idea maps to the documentation pass. As an
arm it is a pre-step variable and widens v2 past fix and re-run. It is post-run
here because the review feeds a v3 decision on a scaffold-first arm, not a v2
cell.

## Declined

Proposed by agents in handoffs, not asked for, not in v2: oracle availability as
a controlled variable; a slimmer image for the no-tests arm; proxy sidecar
hardening; digest-pinned base images; `--read-only` rootfs; a second library;
n=10.

Also agent-proposed, and pulled from this plan on 2026-09-16 when Kevin asked
what it was: writing the derivation cache key into each run's manifest. The key
is `compute_derivation_cache_key` in gbnf-experiment's `config.py`, a 16-hex
sha256 of the pinned gbnf commit plus the derivation Docker context. It names
the cache directory the reference is built into and copied from. It entered the
repo in the initial commit, so its authorship is not in the history. It matters
to v1 only because the `.pyc` leak was per cache directory: one key was poisoned
by a host `pytest` run, another was clean, and no manifest says which a run
used. Under the whitelist a poisoned cache cannot reach the mount, so the
provenance gap loses its teeth. Kevin can pull this back if he wants it.

Also closed by Kevin earlier and not to be re-raised: sanitizing the reference;
dirty-tree recording; max-turns exhaustion detection; `/goal`.
