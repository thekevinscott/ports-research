## Process

**Journal.** `JOURNAL.md` at the repo root. Append-only, one entry per major
event, UTC timestamp on each. Lab notes, not a changelog: what was done, what was
found, what was decided. Agents and Kevin both write to it. Session handoffs
under `internal/` keep their job, which is carrying state between sessions.

**Branches.** Every change is a branch in `.worktrees/<branch>`, the branch and
directory named identically, dashes only, opened as a PR. Kevin merges. The rule
already exists verbatim in agent-transcript-viewer's `AGENTS.md`; the next PR
copies it into this repo's `AGENTS.md` and adds `.worktrees/` to `.gitignore`.
Run data is committed and the pack is 23 MB, so a worktree checkout is cheap.

**One concern per PR.** Splitting is cheap and reviewing is not.

## Harness

**Whitelist.** The agent's tree is assembled by `shutil.copytree` over the
derived source, followed by three removers. `remove_colocated_tests.py` globs
`*_test.py` and `*.test.ts`, so bytecode under `__pycache__` survived and four
runs decompiled it. The fix is an allow set per language over the copy: only
paths matching the set are copied, everything else is left behind and counted
in the manifest. The library itself is not touched; footnote 2 of the post still
holds.

> I chose a blacklist rather than a whitelist because I wanted to modify the
> underlying library as little as possible, to remain faithful to the original
> impetus of acting on an entirely pre-agentic library.

First test is a fixture tree with a `__pycache__/*_test*.pyc` entry, red before
green. The existing `TREE` fixture in `remove_colocated_tests_test.py` has no
such entry, which is why the unit tier never caught it.

Two deferred decisions land in the same PR series:

- The reference's `pyproject.toml` `testpaths`, its `Makefile` test targets and
  `vitest.config.unit.ts` `include` still advertise the withheld test layout.
  The 2026-09-07 note said "Raise it with Kevin if that signal matters."
  Decision owed: strip them under the whitelist, or accept the disclosure.
- The manifest records no derivation key. The contaminated tree was identified
  after the fact only because it happens to name its suites `tests/javascript`.
  Grading also computes the key live rather than reading the run's. Write the
  key into every manifest.

**Prompt.** The second line, "Run tests/ and iterate until green", points at a
directory that `assemble_reference_implementation.py` creates empty and the
harness mounts read-only. All five no-tests runs wrote there, hit `EROFS`,
probed `mount`, and relocated. In the target-tests cell the provided suite was
green on first invocation in five of five runs. Neither cell exercised
iteration. Decision owed before the re-run: keep the line, drop it, or omit the
mount when no suite is included.

**Redo scope.** The 2026-09-14 notes left "surgical 8 vs full re-run" as
Kevin's call. The whitelist settles it: any assembly change moves the corpus the
model sees, so every v1 run becomes a prior harness generation. Full re-run of
the 40 under one pinned harness and one derivation key, tagged `v2`. v1 median
was 6.5M tokens and 13 minutes per run.

## Analysis

**Learning track, not a build track.** Embeddings and AST metrics both exist and
neither has a reading Kevin trusts.

> I don't want to drop it but I want to ignore it for now

> I'm still not sure how to interpret any of the AST stuff

The literature review (`internal/LITERATURE_2026-09-09-code-embeddings.md`, 43
references) found embeddings track surface similarity, not correctness, and
recommended calling the measure structural drift. Seven AST measures including
cyclomatic complexity are computed for every run and displayed nowhere; the
notebook shows only file count and LOC. Deliverables, in order: the
plain-language explainer Kevin asked for on 2026-09-10 ("how to tell whether
something is close or not, in a way that a mid-to-senior SWE can understand"),
then a decision on which measures reach the notebook.

**Literature.** Already done. Read `internal/LITERATURE_2026-09-09-code-embeddings.md`,
`SYNTHESIS.md`, `internal/LANDSCAPE.md`, `papers/INDEX.md`. No new work.

**Mistral.** Their case study (mistral.ai/news/legacy-code-modernization/) did
three things: a numerical parity harness before any translation; a documentation
pass where 100+ agents worked leaf-up over a caller-callee tree; and a
human-supervised coder/tester/reviewer loop after a fully autonomous pass
produced "Fortran retyped in C++ syntax". The scaffold idea maps to the
documentation pass. As an arm it is a pre-step variable and widens v2 past fix
and re-run. Decision owed: v2 or v3.
