Written 2026-09-16, the day after the v1 post went up. v1 is tagged `v1` on
`f21cd76`. The mandate for v2, from the 2026-09-13 session:

Everything in this plan was either asked for on 2026-09-16 or is quoted from an
earlier session. Ideas an agent proposed without Kevin asking are listed at the
end, declined, so they are not quietly re-proposed later.

Notes cited as `internal/...` are gitignored working files on Kevin's machine.
They are named so he can find them. They are not in this repo.

The plan is in four sections. Preparatory work is everything that has to be
true before a v2 run is banked. Running is the agents, the models, and the
re-run itself. Analysis is everything done to the banked runs. After v2 is the
outside reading, held back so it cannot steer the analysis.

## Process

Applies to all four sections.

**Journal.** `JOURNAL.md` at the repo root. Append-only, one entry per major
event, UTC timestamp on each. Lab notes, not a changelog: what was done, what was
found, what was decided. Agents and Kevin both write to it. Session handoffs
under `internal/` keep their job, which is carrying state between sessions.

**Branches.** Every change is a branch in `.worktrees/<branch>`, the branch and
directory named identically, dashes only, opened as a PR. Kevin merges. The rule
already exists verbatim in agent-transcript-viewer's `AGENTS.md`; the first PR
after this one copies it into this repo's `AGENTS.md` and adds `.worktrees/` to
`.gitignore`. Run data is committed and the pack is 23 MB, so a worktree
checkout is cheap.

**One concern per PR.** Splitting is cheap and reviewing is not.

## Preparatory work

Order matters within this section. Each item is one or more PRs.

### 1. Whitelist

The agent's tree is assembled by `shutil.copytree` over the derived source,
followed by three removers. `remove_colocated_tests.py` globs `*_test.py` and
`*.test.ts`, so bytecode under `__pycache__` survived and four runs decompiled
it. The fix is an allow set over the copy: only paths matching the set are
copied, everything else is left behind and counted in the manifest. The library
itself is not touched; footnote 2 of the post still holds.

> I chose a blacklist rather than a whitelist because I wanted to modify the
> underlying library as little as possible, to remain faithful to the original
> impetus of acting on an entirely pre-agentic library.

Kevin, 2026-09-16:

> the whitelist should be made generic, and there should be a way to define it
> from gbnf-experiment

So the mechanism and the set live in different packages. Today porting-harness
takes a finished tree and knows nothing about how it was assembled; every
remover is gbnf-specific code in `gbnf_experiment/prepare_filesystem/`. Under
the whitelist, porting-harness owns the copy-by-allow-set step and its tests,
with no knowledge of gbnf. gbnf-experiment passes the set, which is the only
place gbnf's layout is named. The three removers go away; what they removed is
whatever the set does not name.

First test is a fixture tree with a `__pycache__/*_test*.pyc` entry, red before
green. The existing `TREE` fixture in `remove_colocated_tests_test.py` has no
such entry, which is why the unit tier never caught it.

One deferred decision lands in the same PR series. The reference's
`pyproject.toml` `testpaths`, its `Makefile` test targets and
`vitest.config.unit.ts` `include` still advertise the withheld test layout. The
2026-09-07 note said "Raise it with Kevin if that signal matters." Decision
owed: strip them under the whitelist, or accept the disclosure.

Decided 2026-09-17, in the whitelist PR review. Colocated tests (`*_test.py`,
`*.test.ts`) are withheld under every condition; the negation is part of each
package's pattern list, not a conditional. A tests flag means one thing in v2:
the generated suite for that language is mounted under `tests/`. In v1 a flag
also kept the reference's own colocated tests in place, so a v1 tests cell and
a v2 tests cell are not the same treatment. The typescript `Makefile` is off
its list; the python `Makefile`, `pyproject.toml` and `vitest.config.unit.ts`
still ship and still name the withheld layout. Disclosure accepted.

### 2. Prompt

Today it is two lines:

```
Port reference_implementation/ to {target_language} in ported_implementation/.
Run tests/ and iterate until green.
```

The second line points at a directory that `assemble_reference_implementation.py`
creates empty and the harness mounts read-only. All five no-tests runs wrote
there, hit `EROFS`, probed `mount`, and relocated. In the target-tests cell the
provided suite was green on first invocation in five of five runs. Neither cell
exercised iteration. Kevin, 2026-09-16: "we'll want to update the prompt too".
The new wording is settled in its own PR, and one wording runs across every arm.

### 3. API coverage tier, and removing the shim

A test suite over gbnf's public surface: exported names, signatures, and
behavior at the boundary. Separate from the integration suite, which drives
behavior and says nothing about how it is reached. Kevin, 2026-09-16: "I want to
be able to remove the shim".

The shim is `execute-test-suite`'s adapter pair, `adapt_python.py` and
`adapt_typescript.py`. It exists because, in the post's words, "Ports not
provided target tests often got behavior right and API surface wrong", and the
integration suite could not run against them unadapted. It rewrites a port's
surface onto the reference API at grading time and records which rules fired.
The 2026-09-07 note that asked for "exercising the public API surface (i.e.,
SDK)" was tabled then as "most dubious"; it is now in.

Two things follow. A port that passes the API suite needs no adapter, so the
adapter and its rules can go, and the graded result is the port as the agent
left it. And the API suite ships in the agent's `tests/` mount whenever the
integration suite does. Kevin, 2026-09-16, on the proposal to hold the graded
suite out of the mount: "if tests are available then the agent should use
them!" Kevin confirms in the API PR.

### 4. Transcript viewer

### 5. Protocol

Proposed by the agent (Claude), not by Kevin, on 2026-09-16, after a review of
the v1 manifests. Kevin: "protocol - totally. write this into the plan. state
very clearly that it is your idea and initiated by you but I approve it and
think it's a good idea."

The v1 harness was pinned nowhere. Across the 42 banked manifests: 16 distinct
harness commits, 27 runs from a dirty tree, 41 distinct sandbox image ids.
Cells ran in the same order inside every block. One cell has seven runs because
failed runs were replaced there and nowhere else, under no written rule.

Before the first v2 run, a protocol is written, committed and tagged. It fixes:
the cells and n; the primary outcome; the exclusion and replacement rule for a
run that dies; the stopping rule; the analysis. The harness refuses to start
from a dirty tree, records one commit and one image digest for every run, and
shuffles cell order within each block.

### 6. Validate the grader

Proposed by the agent (Claude), not by Kevin, on 2026-09-16, from Anthropic's
migration post: "a judge that doesn't catch breakage isn't a judge." Kevin:
"'validate the grader' - equally good! phenomenal idea. same thing."

The grade is the derived suite's pass rate. Its sensitivity is unmeasured. Once,
before the re-run: copy the reference to scratch, mutate it a handful of ways
(flip an operator, drop a branch, shift a bound), and run the derived suite
against each mutant. Record which mutants it catches and which survive. The
reference in the tree is never touched. Zero runs.

### 7. Thinking text

Every `thinking` block in every banked v1 transcript is
empty: text `""`, plus an encrypted `signature` whose length tracks the billed
thinking tokens. Kevin, 2026-09-16: "add this to the list of things to fix",
and "I want to capture thinking and assume its a bug that we're not?"

It is not a harness bug. Re-counted 2026-09-16 over 103,338 Claude Code
transcript files on Kevin's machine: `claude-opus-5` through the first-party
API wrote text into 0 of 8,931 thinking blocks. Fable models wrote text into a
few percent of theirs. And 16 blocks from Claude Code pointed at openrouter,
model id `anthropic/claude-opus-5`, all carry text alongside the signature.
Same CLI, same model, different transport, text present. The redaction is on
the first-party path. Why is not visible from here.

So the lever is transport. Kevin, 2026-09-16: "Thinking investigation needs to
be part of v2 prepatory". The investigation, before the re-run: run the same
short prompt through Claude Code on the first-party path and through openrouter
and compare the banked blocks; find whether any CLI or API setting restores the
text on the first-party path; record what Codex writes for reasoning. Outcome is
a note in the repo saying, per agent and route, whether v2 transcripts will
carry thinking text. No agent is gated on it; the answer is recorded as a
property of that agent.

**The judge.** Kevin's check-in oracle (see earlier asks), run after the fact

### 2. Statistics

Kevin, 2026-09-16: "You are fully in charge of statistics. You tell me what you
propose whenever it comes to stats. I have zero stats background." So this
section is the agent's (Claude's) proposal, and it is written into the protocol
before run one.

- Fewer cells, not more runs. Eight cells of five cannot be told apart by any
  test. Two cells per direction, ten runs each, from the same 40.
- One primary outcome per run, named in the protocol: the derived suite's pass
  rate, unadapted, once the shim is gone.
- The test is a permutation test on the difference in medians: shuffle the cell
  labels many times and count how often a gap as large as the observed one
  arises. No distribution is assumed, which is the right choice at this size.
- Report the observed gap with a bootstrap interval, not a p-value alone.
- State the minimum detectable gap up front, so a null reads as "too small to
  see with 10 vs 10", never as "no effect".
- Charts stay per-run dots with median ticks. No mean bars.

### 3. Embeddings and AST

A learning track, not a build track. Embeddings and AST metrics both exist and
neither has a reading Kevin trusts.

> I don't want to drop it but I want to ignore it for now

> I'm still not sure how to interpret any of the AST stuff

The literature review (`internal/LITERATURE_2026-09-09-code-embeddings.md`, 43
references) found embeddings track surface similarity, not correctness, and
recommended calling the measure structural drift. Seven AST measures including
cyclomatic complexity are computed for every run and displayed nowhere; the
notebook shows only file count and LOC. Deliverables, in order: the
plain-language explainer Kevin asked for on 2026-09-10 ("how to tell whether
something is close or not, in a way that a mid-to-senior SWE can understand"),
then a decision on which measures reach the notebook.

### 1. Mistral review

Their case study (mistral.ai/news/legacy-code-modernization/) did three things:
a numerical parity harness before any translation; a documentation pass where
100+ agents worked leaf-up over a caller-callee tree; and a human-supervised
coder/tester/reviewer loop after a fully autonomous pass produced "Fortran
retyped in C++ syntax". The scaffold idea maps to the documentation pass. As an
arm it is a pre-step variable and widens v2 past fix and re-run. The review feeds a v3
decision on a scaffold-first arm, not a v2 cell, and Kevin wants it read after
the v2 results for the same reason as the literature: "same with mistral".
